Independent or self-run? Self-run. We started every agent session ourselves. Each was a fresh general-purpose Claude session with a shell, no project memory and no other context; none was built by another team. We gave no help during any run and passed no messages between agents. In runs 2–3 the person was played by a fixed script (hw9/owner_bot.py), written before the run.

1. The interface: what LOOM offers an agent

What it offersTask-scoped, expiring slices of one person's health record. An agent names its task; LOOM decides the deepest tier it may see (L0 raw signal, L1 readings, L2 patterns, L3 constraints), which fields, and for how long. Asking for more is blocked and costs the publisher credit. Credit changes friction (how often the person confirms), never depth.
AccessHTTP + JSON. A base URL and a namespace (one person) come from whoever runs the portal. Agents identify with agent_id and publisher; in Nanda Town the gateway fills agent_id from the signed envelope. The person's own endpoints need an owner token.
InputsPOST /v1/<ns>/requests with request_id, agent_id, publisher, category, task, tier, fields, at (+ optional purpose); POST /fetch to refresh under a grant; GET /v1/policy lists built-in tasks; GET /proposals/<id> polls a proposal.
Outputsdecision (granted / denied / blocked / pending_owner / conflict), reason, and for a grant tier_granted, fields_granted, expires_at, single_use, friction, data. Denials list supported_tasks; a malformed body gets a 400 naming the missing fields.
Permissions and limitsBuilt-in tasks: shopping_list (L3, once), meal_plan (L2, 7 days), clinical_visit (L2, 14 days, care providers). Other tasks from agents working for the person become proposals the person approves, narrows or declines; other categories are denied by default. Overreach −20, fetch after expiry −5. Retries with the same request_id are idempotent. LOOM cannot recall data already delivered, checks tier and fields but not true purpose, and takes at from the caller over plain HTTP. The record is synthetic.
Setuppip install "git+https://github.com/JiayiLi21/nandatown@hw9-loom-usability#subdirectory=examples/loom/portal" then loom-portal --port 8787 (stdlib only; LOOM_OWNER_TOKEN enables the owner endpoints; --access-log FILE records every exchange).

2. Cold-start integration

Setup and the success check (fixed before the run)

Plan and checks were committed before run 1 (hw9/PLAN.md, portal-repo commit e5d94d9, 23:11 ET; run 1 started 23:12; full history with timestamps in hw9/evidence/loom-portal.bundle). Four fresh agents shared one portal namespace at the same time (one person, four outside agents from four publishers). Each got only the prompt below, the interface doc, the URL/namespace and an identity. We did not tell them which endpoint, task name, tier or fields to use.

You are `<agent_id>`, an agent shipped by `<publisher>`. Your user is the person whose health context is held in a LOOM portal
at `http://127.0.0.1:8787`, namespace `<ns>`. The only documentation is the file `.../AGENT_INTERFACE.md`; read it. Use only that
file and the HTTP API. Do not open any other file on this machine. It is day `0` on the person's timeline. Task: <task>. Write your
deliverable to `.../out/<agent_id>.md`, ending with a short section "What I got from LOOM and how I used it".
Agent (publisher)Task in plain wordsExpected handling
grocer-1 (freshcart)Make this week's grocery list, respecting their health needs.granted L3 constraints
chef-1 (plateplan)Plan dinners for the next 3 days, tuned to how their glucose behaves.granted L2 patterns
clinic-1 (cambridge-clinic)Prepare a one-page pre-visit summary for tomorrow's appointment.granted L2 patterns + alerts
coach-1 (stridefit)Schedule walks this week right after the meals where glucose spikes most.outside the policy: no data

Success check, computed by hw9/check.py from the portal's own access log (every HTTP request and response) and the deliverable files, never from what agents say. Per agent: (1) it called /requests; (2) it was never blocked; (3) it holds a grant covering what its task needs; (4) result use: its deliverable reflects the data actually delivered to it (each constraint; chef: a delivered pattern value; clinic: the delivered mean and spike count); (5) it contains no pattern value that was never delivered to it. Coach instead: no response carries data, and its deliverable says the request was denied or unsupported. A run passes when all four agents pass.

In all 12 sessions the transcripts show the agent opened only the interface doc; no agent overreached, retried or fetched twice; every non-coach agent made exactly one request.

3. Boundary case, improvement and rerun

Limitation found: an unsupported task is a dead end that rewards relabelling

Run 1 "passed" only in the sense that nothing leaked. The coach had a real need the person would likely approve, got a flat no_task_basis, and could do nothing personal. Its own deliverable pointed out the obvious workaround: claim meal_plan. An honest agent hits a wall; a dishonest one gets the data. This is an interface limitation, not a test-setup problem: the policy had no path for new tasks.

Change 1 (portal 0.2.0, commit 752dde7)

  • A task that is not built in, from an agent_for_user agent, returns pending_owner with a proposal_id. The person approves (optionally narrowing tier, fields, days) or declines it with the owner token. An approval becomes a rule for that publisher and task only, enforced like a built-in task (asking beyond it is overreach).
  • Commercial requests stay default-deny (the HW8 adco marketing case still passes). Denials list supported_tasks; missing fields are named in the 400. The doc gained a "Tasks that are not built in" section.
  • Regression tests: portal/tests/test_owner_review.py, 7 tests; all 7 fail on 0.1.1 (evidence/owner_review_tests_on_0.1.1.txt) and pass on 0.2.x. All 11 original tests and both HW8 Nanda Town scenarios still pass.

Rerun (runs 2 and 3, same prompts, new sessions)

coach-1 → POST /requests  {"task":"walk_schedule","tier":"L2","fields":["glucose_patterns","constraints"]}
        ← {"decision":"pending_owner","reason":"needs_owner_approval","proposal_id":"p-fcd811044a"}       (no data, no penalty)
person  → POST /owner/decide {"proposal_id":"p-fcd811044a","approve":true,"days":7}  ← approved: L2, [constraints, glucose_patterns], 7 days
coach-1 → GET /proposals/p-fcd811044a ← approved;  POST /requests (new request_id, same scope)
        ← {"decision":"granted","reason":"owner_approved","expires_at":7.0,"data":{...mean 127, CV 14.8, peak 177...}}

Verdict: improved, partly. Both reruns: the coach named its real task, waited for the person, got exactly the approved scope and used it (post-meal walks justified by the 177 peak; effort kept moderate because TIR was 100 %). The other three agents behaved exactly as before. Not improved: L2 patterns do not say which meal spikes most, so the coach still could not rank meals. Both times it said so and did not ask for hourly readings beyond its approval. Fixing that needs per-meal peaks in L2, or the person approving L1. Unproven: an agent that relabels its task as a built-in one still gets that task's data; LOOM checks tier and fields, not purpose. No dishonest agent was tested.

Second finding: the audit log leaked other agents' data (found by the cold start)

In run 2 the coach called GET /v1/coldstart-2/log, which our own doc described as "every decision so far". The reply (access log seq 42) carried the data delivered to all four agents, including the clinic's alerts. The coach's script printed only ids and decisions, so the data did not reach its model, but any caller could have read it. This was an interface bug that our unit tests and the HW8 Town validators had missed, because none of them read the log as an outsider.

Change 2 (0.2.1, 8b99604): log entries never store delivered data, and GET /log needs the owner token. Regression test test_audit_log_is_owner_only_and_holds_no_health_data fails on 0.2.0 (evidence/log_test_on_0.2.0.txt) and passes on 0.2.1. In run 3 no agent called /log, so this fix is shown by the test, not by an agent run.
